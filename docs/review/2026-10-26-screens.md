# Review notes, screens, 26 October 2026

**S-40. Redirect signed-out home visits before waiting for protected master data.**
The local backend was healthy, with valid CORS headers, but GET /auth/me and /master-list
returned 401 without a valid cookie. The home page waited for both the user and master-list
state before choosing a route. A rejected master request left its state undefined forever,
preventing the sign-in redirect and displaying a misleading backend-connection error.

The home page now waits for auth first and redirects a signed-out user immediately,
independently of protected data. Master-list failures are shown only to authenticated users;
the existing Retry flow remains available for genuine service failures. Authentication is
still required by the backend. No cookies, credentials, master lists or invoices were changed.

Validation: reproduced the exact message at / in fresh Chrome before the fix. Afterward,
fresh signed-out and invalid-cookie visits redirect to /sign-in. A mocked authenticated
master-list 500 still shows Retry, and recovery to an empty list opens the upload screen.
No browser page errors occurred. All 114 frontend tests, TypeScript and lint of the changed
page passed. The running Next.js development server loaded the change automatically.
Browser results/screenshots are in ignored backend/runtime/auth-redirect-20261026/.

**S-41. Keep local frontend/API cookies on the same hostname and verify sign-in.**
Both local services were healthy, but Chrome at localhost:3000 called the configured API
at 127.0.0.1:8001. Reproduced POST /auth/sign-in 200 followed by GET /master-list 401, with
no accepted session cookie. The SameSite=Lax cookie could not establish this cross-site
fetch session. This differs from S-40's signed-out home redirect: here the frontend already
believed sign-in had succeeded and therefore continued to show the data error.

The service URL now matches the browser hostname when both endpoints use localhost or
127.0.0.1, preserving the API port and base path. Relative proxy and remote API settings
are unchanged. Cookie/CORS security settings were not relaxed. Sign-in now verifies the
HttpOnly cookie through /auth/me before accepting the login. Removed the offline fallback
that invented a signed-in user from browser-bundled default credentials when requests failed.

Validation: all 119 frontend tests, TypeScript and targeted lint passed. Added regressions
for loopback host matching, preserved remote/proxy URLs, blocked session cookies and an
unreachable login backend. Chrome verified real configured login, successful protected reads,
refresh persistence and logout at both http://localhost:3000 and http://127.0.0.1:3000, with
no page errors. Credentials were read only into the test process, never displayed or saved.
No invoices or master lists were changed. Browser evidence is in ignored
backend/runtime/localhost-cookie-20261026/. The production build also passed; both servers
still returned HTTP 200 afterward. The dev server loaded the fix automatically.
