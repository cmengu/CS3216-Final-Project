# Review notes, screens, 11 October 2026

A review of pull requests #3 and #9 to #11 against the feature PRDs F-01, F-07, F-08 and F-09,
followed by fixes. Every edit has a numbered note here. So does every point where the reviewer
disagreed with the code and left it alone for its owner.

Read this before changing `src/checker/` or `src/components/pages/invoices/`. When you act on a
note, delete it or write what you did under it. The backend has its own file,
`2026-10-11-backend.md`.

Checked on this branch: `npm test` gives 184 passed, `npm run typecheck` and `npm run lint` are
clean, and `node scripts/e2e.mjs` passed every check against a running app and a service on
replayed answers. The walk's upload step was skipped, so as not to add an invoice to a service
someone else was using.

## Verdict

Upload, the list and the invoice page were wired to the service, with no fallback to sample
invoices. Five things did not meet the PRDs: the browser still added up overcharge when the
service sent no total, a failed upload disappeared, a failed invoice gave no reason, the upload
time was compared with a fixed sample date, and the list stopped at 50 invoices. All five are
fixed below. The list still makes one request per invoice (SD-01), which needs a change on the
service.

## 1. Changes made

**S-01. The browser no longer works out overcharge for a service invoice.**
`src/checker/summary.ts`, `lineOver` and `overcharge`. The line figure is the service's own
`overcharge`, and the invoice figure is the service's `overcharge_total`. When the service
claims nothing, the screen shows nothing; it used to add the lines up itself, which is what
F-08 forbids. One visible effect: 0.015 over on 67 pieces showed 1.00 from browser arithmetic,
and now shows the service's 1.01. Only a sample invoice, which has neither field, is still
added up, and no screen loads one. Tests in `src/checker/convert.test.ts`.

**S-02. The service's warnings reach the page.** `src/checker/convert.ts` keeps
`check.warnings`, and `InvoiceView.tsx` shows them under the count of problem lines. This is
where "1 line not priced" and "Invoice arithmetic does not reconcile" appear.

**S-03. Each result is paired with its line by the service's line number.**
`src/checker/convert.ts`. They were paired by position in the list. A line with no result is
still shown as Needs a person, now with the reason "The check gave no result for this line."

**S-04. A failed invoice says why.** `convert.ts` keeps the service's `error`, and the invoice
page and the list row show it, for example "Could not be checked. reading: No readable text or
tables". They used to say "could not be read" whichever step failed. A status the screen does
not know is shown as failed and named, where it used to show as still checking forever.

**S-05. A failed upload opens its saved invoice.** `src/checker/api.ts`, `uploadInvoice`. The
service keeps an invoice it could not check and answers 422 with the saved record. The screen
used to show one generic sentence and never reload, so the invoice did not appear. It now
reloads the list and opens that invoice, whose page gives the reason.

**S-06. A refused file shows the service's own sentence.** `uploadFailure(status, detail)`. For
a file the service did not keep, such as an encrypted PDF or one over 30 pages, the screen now
shows "This file could not be checked. PDF must contain 1–30 pages". A server error reads "The
checking service had a problem", where it used to read "could not be reached".

**S-07. The file is checked before it is sent.** `uploadProblem` in `api.ts`. A file that is
not a PDF shows "Only PDF files can be checked." and nothing is sent, as F-01 scenario S-02
says. A file over the service's 20 MiB limit shows "That PDF is over the 20 MB limit." There
was no size check, and the wording was "Choose a PDF."

**S-08. A second file cannot be sent while the first is uploading.**
`InvoicesView.tsx`, the `sending` ref. The `busy` state updates a moment late, so two files
dropped together could both be sent.

**S-09. The upload time uses the real clock.** `uploadedLabel` in `summary.ts`. The list
compared the upload date with the sample data's fixed "today" of 1 October 2026 and sliced a
UTC time out of the text, so a real upload never showed "Today 10:42". Test in
`src/checker/summary.test.ts`.

**S-10. The list asks for every page.** `listInvoices` in `api.ts`. The service gives 50
invoices unless asked and at most 100 at once. Invoice 51 onward was silently dropped, so the
piles, "Overcharged so far" and the menu count were all short. Test:
"asks for every page".

**S-11. The fixture mark shows in every state.** It was a few words inside a hint on a checked
invoice only. It is now a label in the invoice page's header in every state, and a note on the
list's heading whenever any listed invoice is a replayed answer.

**S-12. An invoice still being checked is read again every three seconds.**
`useRemoteInvoice` in `api.ts`. F-08 asks for "a Processing state that refreshes by itself".
The list does not do this yet (SD-02).

**S-13. The invoice page reads one invoice, not the whole list.** `InvoiceView.tsx`. It loaded
every invoice as a fallback and showed a cached copy when the direct read failed. It now says
the service could not be reached.

**S-14. Reads give up after 15 seconds.** `api.ts`, `read`. A hung service left the pages
loading forever. An upload has no limit, because a first check can take over a minute.

## 2. Disagreements left for the owner

**SD-01. The list makes one request per invoice.** `listInvoices` reads every invoice in full
to get its supplier, number and overcharge, because the service's summary has none of them.
The menu's count does the same on every page, for every role. At 500 invoices that is over
500 requests per page view, against F-09's "loads in 2 seconds with 500 invoices". The fix is
three more fields on `InvoiceSummary` in `backend/api/contracts.py`, which the shared rule
says not to change without asking. Owners: Duc for the fields, Nam for the list.

**SD-02. The list does not refresh by itself.** F-09 asks for it while any invoice is being
checked. It was left out because each refresh costs the requests in SD-01. In release 1 an
upload waits for its result, so a checking row only appears when a second window uploads.

**SD-03. Wording and layout differ from F-08 and F-09.** A clear invoice reads "Every line
matches" and "3 match", where the PRD has "Clear" and the number of lines. Matching lines are
listed in the left-hand table, where the PRD folds them behind a count; dummy invoice 10 has
36. A list row has no invoice date, and its status and overcharge share one label. Left for
Nam: these are design choices on a screen that already tests well.

**SD-04. The walk in `scripts/e2e.mjs` can pass when the upload is broken.** It skips the
upload silently when the PDF is missing (line 152), passes when the service is down (lines 129
and 157), waits for any button containing "Checking", which the Checking pile also matches
(line 156), and expects the words "Fixture answers", which fails once the service runs live
(line 165). It has no wrong-file case. Both walks also ignore every console error that
mentions port 8000, with the port written into the script.

**SD-05. Sample invoices are kept only for tests.** `src/checker/sample.ts` is imported by
`summary.test.ts` alone. The optional `overcharge`, `overchargeTotal` and `fixture` fields in
`types.ts`, and the sample branch in `lineOver` and `overcharge`, exist only for it. Moving
those tests to service-shaped invoices would let all of it go, and with it the last arithmetic
on money in the browser.

**SD-06. The conversion lives in `src/checker/convert.ts`.** The plan names
`src/checker/api.ts`. It is still one file, and "no other file needs the service's names"
holds except for the `id` read at the top of `listInvoices`.

**SD-07. The service address is fixed when the app is built.** `NEXT_PUBLIC_INVOICE_API` is
written into the bundle, so a build made without it ships `http://127.0.0.1:8000`, including
to Vercel. The service in turn accepts requests only from port 3000 on this machine
(`backend/api/app.py`). Both are fine for a demo on one laptop and wrong for anything hosted.

**SD-08. The side menu still says "PO Tracker" and names the order demo's company.** The
release-1 plan assumes the product is shown as "Invoice Checker" and opens on Invoices.

**SD-09. Smaller things.** `api.ts` holds the requests, a cache, a reload signal, two hooks and
the error sentences in one file. The two hooks are near copies. Money is a plain `number` on
the screen side; it is only displayed now, never added.

## 3. What the review agents reported

Two independent reviews ran on this stack: one against the repo's documented standards, one
against the PRDs. Their findings are the changes and disagreements above. Confirmed and needing
no action: the drop area and the file picker both exist, a 201 reloads the list and opens the
invoice, no screen imports the sample invoices, the three piles and the status mapping are
right, and the dynamic route awaits its `params` as this version of Next requires.
