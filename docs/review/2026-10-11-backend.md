# Review notes, backend, 11 October 2026

A review of pull requests #2 and #4 to #8 against the feature PRDs F-03 to F-07, F-10 and F-11,
followed by fixes. Every edit has a numbered note here. So does every point where the reviewer
disagreed with the code and left it alone for its owner.

Read this before changing `backend/check/`, `backend/eval/`, `backend/extract/` or
`backend/api/`. When you act on a note, delete it or write what you did under it. The screens
have their own file, `2026-10-11-screens.md`.

Checked on this branch: `pytest -q` gives 96 passed and 4 skipped (the skipped ones need Docling
weights or a model key). `ruff check .` and the README's `ruff format --check` both pass.

## Verdict

The line results were right on all ten dummy invoices before this review. Four things were
wrong or missing: nothing connected the real steps to the service, the overcharge total went
empty whenever one line could not be priced, the price sheet loader only accepted the dummy
sheet's exact layout, and the scorer crashed when the model returned fewer lines than the
answer file. All four are fixed below.

The larger finding comes from the mock invoice set (section 4). With every field read
perfectly, today's rules give the right result on 16 of its 58 lines. The other 42 need
decisions the team has not made yet (section 5).

## 1. Changes made

**B-01. The service can run the real steps.** `api/live.py` adds `LiveStages`, and
`INVOICE_MODE=live` with `INVOICE_PRICE_SHEET=<path>` selects it in `api/app.py`. Before this,
only fixture mode could be chosen, so no invoice the system had not seen could be checked.
Live mode refuses to start without a named price sheet: a default would let the wrong sheet
price invoices silently. An unknown `INVOICE_MODE` also stops the start. Tests:
`test_live_mode_*`, `test_an_unknown_mode_*` in `tests/test_api.py`. Not yet run against a
real model, because no key was available.

**B-02. A failed invoice says which step failed and why.** `api/app.py` now stores
`"reading: No readable text or tables; …"` in place of `"ValueError: processing failed"`. Only
a step's own `ValueError` sentence is shown. A pydantic validation error is also a
`ValueError` and quotes the value it rejected, so it keeps the generic text. F-10 asks for
"Failed, with the step and the reason". Tests: `test_a_step_that_gives_its_reason_*`,
`test_a_rejected_shape_*`.

**B-03. The overcharge total is the sum of the known overcharges.** `check/compare.py`. Lines
with no known price are left out and counted in `warnings`, as `"1 line not priced"`. This
settles the F-07 conflict the way the release-1 plan assumed, and it needs no change to
`api/contracts.py`, because the count travels in the existing `warnings` list. The total is
still empty when the invoice's own sums disagree: nothing is claimed on an invoice that cannot
be trusted. `dummy/cases.py` and `data/dummy/manifest.json` were updated to match: invoices 03
and 04 now expect `0.00`, invoice 06 expects `15.00`, each with its warning. Fixture mode
replays these new answers. Test: `test_the_total_is_the_known_overcharge_*`.

**B-04. An invoice is reconciled on what it prints.** `check/compare.py`,
`_invoice_sums_disagree`. Before, an invoice with no tax line or no subtotal had every line
stopped with "Invoice arithmetic does not reconcile". Commercial and proforma invoices often
print one total and nothing else. Now a missing tax counts as no tax, and a missing subtotal
means the lines must add up to the total. An invoice with no total at all is still stopped. If
the model misses a tax line that was printed, the sums no longer agree and the invoice still
goes to a person. Tests: `test_an_invoice_that_prints_no_subtotal_or_tax_*`,
`test_lines_that_do_not_add_up_*`, `test_an_invoice_with_no_total_*`.

**B-05. Subtotal plus tax is checked even when a line total is missing.** Same function.
Before, one missing line total skipped both invoice sums, so subtotal 100, tax 0, total 999
passed. Test: `test_subtotal_plus_tax_is_still_checked_*`.

**B-06. A line with no part number is an Unknown part.** `check/compare.py`. It was "Needs a
person: Part number is missing". The PRD says both in different places; the decision table in
F-05, scenario S-02 in F-03 and section 8.2 of the release-1 plan all say Unknown part, so
that is what the code does. Test: `test_a_line_with_no_part_number_*`.

**B-07. A quantity of zero or less goes to a person.** `check/compare.py`. A negative quantity
priced above the sheet used to give a negative overcharge, which lowered the invoice total.
This is a new rule the PRD does not have. Credit notes will need their own rule (Q-6). Test:
`test_a_quantity_below_zero_*`.

**B-08. A missing currency has its own reason, and no difference is given across two
currencies.** `check/compare.py`. A missing currency used to read "currency differs". A USD
invoice against an SGD price used to report a per-unit `difference` between the two numbers.
Tests: `test_a_missing_currency_*`, `test_different_currency_is_not_converted`.

**B-09. The check must be given its price sheet.** `check(invoice, sheet)`. The default that
loaded `data/dummy/price-sheet.xlsx` on every call is gone, with the constant `DEFAULT_SHEET`.
The reason "Part is absent from dummy price sheet" is now "Part is not on the price sheet",
in the code, the generator and the manifest.

**B-10. The price sheet loader reads a real-looking sheet.** `check/sheet.py`. It reads the
first worksheet whatever its name (F-04 says "first worksheet"; the code required a sheet
named "Prices"). It finds the header row within the first 20 rows, so a title above the table
is fine. It accepts several wordings per column, listed in `HEADERS`, such as "Item / part
code" and "Agreed unit price". Tests: `test_a_sheet_with_a_title_*`,
`test_a_sheet_with_no_header_row_*`.

**B-11. A part listed twice at different prices goes to a person.** `check/sheet.py` records
it in `PriceSheet.conflicts`, and the check answers "Price sheet lists more than one price for
this part". Before, the first row won silently. The same part listed twice at the same price
is fine. Tests: `test_the_same_part_at_two_prices_*`, `test_a_part_the_sheet_prices_twice_*`.

**B-12. Price cells are read safely.** `check/sheet.py`, `_decimal`. A text cell "0,0047" was
read as 47; it is now refused. "1,250.00" is read as 1250.00. A tiny number cell such as
0.00005 produced the text "5e-05", which the check result rejected; it is now "0.00005". A bad
cell names its row. Negative prices are refused. Tests: `test_a_price_that_is_not_a_number_*`,
`test_a_very_small_price_*`.

**B-13. The scorer no longer crashes.** `eval/score.py`. Fewer lines than the answer raised
`IndexError`, and one refused extraction ended the whole run with no report. Now a missing
line is scored as wrong, and an invoice a step refuses is listed under "invoices a step
refused" and scored as wholly wrong while the run goes on. Tests: `test_a_dropped_line_*`,
`test_an_invoice_a_step_refuses_*`.

**B-14. The scorer counts invented lines, and compares dates as dates.** A line the invoice
does not print is one wrong field. `2026-10-1` equals `2026-10-01`. Tests:
`test_an_invented_line_*`, `test_a_date_is_compared_as_a_date`.

**B-15. "Fields read correctly" now measures reading only.** It used to mix in the check's
output values, more than half of the count. Those are reported on their own line, "check
results equal to the answer file", which is the release-1 metric "Line results equal to the
answer file". Every miss carries its run number, so three runs of one miss are three distinct
entries. A count of zero prints "nothing to measure", not "100%". The saved JSON now holds the
numbers and the refused invoices, not only the printed text.

**B-16. The scorer command takes its inputs.** `invoice-score --manifest PATH --price-sheet
PATH --runs N`. The defaults are the dummy set. This is what lets it run on another answer
file. Test: `test_the_command_ends_with_an_error_*` also covers the exit code.

**B-17. Readme and formatting.** `backend/README.md` describes both modes, the check's rules,
the scorer and a verify command that covers `check/`, `eval/` and `extract/`. `ruff format`
was run on the files of this stack; `extract/invoice.py` changed by formatting only.

## 2. Disagreements left for the owner

**BD-01. `check` imports its result type from `api`.** `check/compare.py` imports
`api.contracts`, and `api/live.py` imports `check`. It works, but the check cannot be used
without the service package. `CheckResult` and `LineResult` belong beside `schema.py`. Left
alone because the shared rule says not to move `api/contracts.py` without asking. Owner: Duc.

**BD-02. The agreed price echoes the invoice's text when the prices are equal.**
`check/compare.py`, `_prices`. It exists so the dummy answer "0.420" matches a sheet cell that
reads 0.42. It is harmless and commented, but a reader expects the sheet's own text. Removing
it means comparing amounts as numbers in `test_each_dummy_invoice_matches_its_answer`.

**BD-03. The model is always sent `temperature=0`.** `extract/invoice.py:56`. Some models
reject that setting, and every invoice would then fail. F-03 says "where the provider allows".
Decide once the model is chosen. Owner: Chen Meng.

**BD-04. Reading warnings are dropped.** `extract/invoice.py` reads `document.markdown` only.
`backend/README.md` says page warnings such as "No readable content on this page" must reach
the person. They are stored with the document but shown nowhere.

**BD-05. Missing token counts raise.** `extract/invoice.py`, `_token_usage`. The scorer's
"cost per invoice: not available" can therefore never print with the real extract. One of the
two should go.

**BD-06. The scorer's fixture refusal can be bypassed.** `eval/score.py`, `_refuse_fixtures`
catches `FixtureStages` methods passed directly. A function that wraps one is accepted.

**BD-07. Cost is reported in tokens, not money.** `eval/score.py`. A price per token for the
chosen model turns it into dollars.

**BD-08. The scorer lists the schema's number fields a second time.** `eval/score.py`,
`AMOUNT_FIELDS`. A field added to `schema.py` must be added there too, or it is compared as
text.

**BD-09. Smaller things.** `pyproject.toml` lists `openpyxl` twice. The package name `eval`
shadows a Python built-in. `tests/test_price_check.py` and `tests/test_rounding.py` each build
the same record and sheet. `tests/test_extract.py:124-128` accepts two different behaviours.
`backend/invoice_processing/` is the earlier experiment and is still in the tree; the plan
says it is removed once its prompt is reused.

**BD-10. The allowance and the mock set disagree on how to measure a difference.** The PRD
measures on the line: gap times quantity, flagged at one cent. The mock set's own rule flags a
unit-price gap above 0.005. Both give the same answers on the mock set. Left as the PRD has it.

**BD-11. The rule "only files under `data/dummy/` are sent to an AI provider" is no longer
enforced by the code.** Live mode sends whatever is uploaded. The readme says so. The rule
should read "only invented invoices", which is what the release-1 plan's constraint says.

## 4. What the mock invoice set showed

The set is 14 scanned invoices in seven layouts, a master price sheet of 24 rows and an answer
key with seven planted price errors. Every value in it is invented. It is kept out of this
repo, in the git-ignored `data/private/mock_invoice_dataset/`, until the team decides whether
it may be published.

**Reading works.** The repo's reader was run on all 14 scans: 18 to 51 seconds each after the
first, which took 90. Its text holds 57 of the 58 line amounts, 42 of 42 printed unit prices, and every
invoice number, date, total and purchase order number. The sideways layout is read, though its
table comes out turned.

**Part codes are the weak spot.** 15 of 20 printed part codes are found exactly. One layout
reads `N02-I-345240310` as `N02-I- 345240310`, with a space. One code has its letter I read as
the digit 1. The lookup trims and ignores capitals only, so both become Unknown part.

**The master sheet did not load before B-10.** It has a title above its header, a first sheet
not named "Prices", and its own column names. It loads now: 22 parts, no conflicts.

**The price check, given perfectly read fields, is right on 16 of 58 lines** and catches 4 of
the 7 planted price errors. The measurement builds each record from the answer key, keeps only
what the page prints, and runs `check`. The other 42 lines fail for three reasons:

- 22 lines on the steel layout print a description and no part code. The sheet can only be
  searched by part number.
- 16 lines on the freight layout and the courier line print an amount only. Freight prints
  "3.20 M3 @ USD 90.00/M3 @ 1.310000" inside the description, with the amount in SGD. There is
  no quantity field and no unit price in the sheet's currency to compare.
- 4 lines on the hose layout carry a line discount, so quantity times price does not equal the
  line total, and the field list has no place for a discount.

## 5. Decisions waiting

Each needs the owner of `backend/schema.py`, and most need the client. Nothing here was built.

**Q-1. Match by description when no part code is printed** (22 of 58 mock lines). This is
F-22, planned for release 3. The mock set makes it a release-2 need.

**Q-2. Add fields.** A purchase order number on the invoice, and on each line a unit and a
discount. The master sheet is keyed by supplier, purchase order, item, unit and currency; the
field list has none of the first, second or fourth.

**Q-3. Lines that print an amount only** (freight, courier). Either the check accepts a flat
charge and compares the line total with the agreed price, or the model is allowed to return
the rate and the exchange rate it reads and the code multiplies them.

**Q-4. One price per part.** The master sheet lists the same part under two purchase orders.
Today the same price twice is fine and two prices go to a person (B-11). The real rule is
probably "the price for this supplier and this order".

**Q-5. Stray spaces inside a part code.** Ignoring all spaces in the lookup would recover four
mock lines. F-04 says only outer spaces are trimmed.

**Q-6. Credit notes.** B-07 sends a negative quantity to a person.

**Q-7. May the mock set go in this public repo?** Every value in it is invented, but
nobody has confirmed it may be published. Until someone says yes, it stays in `data/private/`.
